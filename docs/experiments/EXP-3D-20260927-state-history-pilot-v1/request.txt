你现在位于仓库：

https://github.com/KennyMcSimpson/measurement-scene-state.git

请在当前仓库基础上完成下一阶段机制实验。

本轮的目的不是追求最好性能，也不是继续扩大二维 selector。

本轮第一次直接检验完整研究方案中的两个核心：

A. 真实目标约束的共享场景状态是否真的成立；
B. 测量反馈驱动的动态测试时写入是否具有“状态/历史相关”的动作价值。

核心研究问题是：

> 模型已经怎样理解了这个场景，会不会决定它看到下一张图时应该怎样学习？
>
> 同一张新图像到来时，不同的已有快速权重历史是否会改变 OFF / fuse / complete / ALL 的相对任务价值？
>
> 如果会，这种差异能否仅通过部署时合法可见的场景预测误差和当前状态统计识别？

这是一轮机制资格实验。

任何负结果都必须保留。

不得为了得到正结果而继续增加 controller、扩大动作空间、改变 backbone、打开封存测试数据或事后修改主要指标。

3. Phase A：静态共享场景状态资格实验

ΔW = 0

目标不是证明“两个 hidden state 完全相等”。

目标是检查：

> 不同局部上下文构建的 query-independent scene state，
> 是否能够通过同一个固定测量程序解释多个未参与状态构建的真实 query。

------------------------------------------------------------
3.1 两个独立上下文
------------------------------------------------------------

对每个 scene：

构造：

context_A
context_B

要求：

- 两组上下文数量尽量相同；

4. Phase B：直接写入与受控历史实验
============================================================

这是本轮最重要的动态 TTT 实验。

核心问题：

> 面对完全相同的下一条视觉证据，
> 不同 fast-weight 历史是否改变后续动作的相对任务价值？

本轮不是简单比较：

sample1 喜欢 fuse
sample2 喜欢 complete

而是更强的：

同一个 observation，
仅因为当前 state / write history 不同，
最优动作或动作排序发生变化。

============================================================
5. 写入动作必须保持原方案定义
============================================================

动作空间固定为：

A0 = OFF
A1 = L_fuse
A2 = L_complete
A3 = ALL

OFF 的定义：

- 新图仍然加入 B_t；
- 正常重新读取 scene state；
- 只是本步不新增 fast-weight write。

绝不能让 OFF 少看一张图。

否则：

OFF vs write

会混入额外 observation exposure。

ALL 必须：

- fuse proposal 和 complete proposal 都从同一个旧 state / old weights 计算；
- 同步 commit；
- complete proposal 不得偷看同一步刚更新的 fuse weight。

新增 regression test。

============================================================
9. 本轮最重要的历史依赖分析
============================================================

不能只检查：

W_FC != W_CF

也不能只检查最终 score 不同。

至少报告四级证据。

LEVEL 1 — Numerical history effect

||ΔW_FC - ΔW_CF||

LEVEL 2 — Prediction history effect

相同 next observation 下：

pre-update / post-update predictions 是否不同。

LEVEL 3 — Action-value interaction

对于任意 action pair a,b：

Gamma(a,b)
=
[G(H_FC,a)-G(H_FC,b)]
-
[G(H_CF,a)-G(H_CF,b)]

报告：

- mean
- sequence bootstrap CI
- per-scene value
- LOSO sensitivity

LEVEL 4 — Decision-relevant state dependence

检查：

argmax_a G(H_FC,a)
!=
argmax_a G(H_CF,a)

同时要求至少其中一个 winning action：

G(H, a*) > 0

不能把：

两个写入都比 OFF 差，
只是 fuse/complete 排序交换

称为“有益的动态轨迹机会”。

22. 阶段判断
============================================================

最终不要只输出 PASS / FAIL。

需要给下面几个独立状态。

------------------------------------------------------------
A. STATIC_STATE_STATUS
------------------------------------------------------------

SUPPORTED
PARTIAL
NOT_ESTABLISHED
BLOCKED

------------------------------------------------------------
B. WRITE_OPPORTUNITY_STATUS
------------------------------------------------------------

SUPPORTED

多个 scene 上存在相对 OFF 的正 task-relevant write opportunity，
且不是单个 scene 支配。

PARTIAL

存在 opportunity，
但分布集中或 CI 不稳定。

NOT_ESTABLISHED

写入 family 几乎没有留出 task headroom。

------------------------------------------------------------
C. HISTORY_ACTION_STATUS
------------------------------------------------------------

SUPPORTED

同一新 observation 在不同历史状态下，
出现稳定的、任务有意义的 action-value 差异；
且多个 scene 中存在 positive beneficial action flip。

PARTIAL

history 改变 reward magnitude / rank，
但真正有益的 winner flip 较少或不稳定。

NOT_ESTABLISHED

history 对后续有益动作选择没有稳定影响。

------------------------------------------------------------
D. FEEDBACK_IDENTIFIABILITY_STATUS
------------------------------------------------------------

SUPPORTED

合法 measurement feedback 能在 heldout development scenes
可靠减少 action regret，
并带来净任务收益。

PARTIAL

存在预测信号，
但部署净收益未稳定成立。

NOT_ESTABLISHED

当前 feedback 无法识别 action utility。

SKIPPED

Phase B 未建立值得学习的 action variation。

25. 最重要的研究纪律
============================================================

不要把本轮设计成：

“怎样让 dynamic TTT 一定成功？”

本轮真正要区分：

CASE A
共享 state 自身没有建立。
→ 修载体，不怪 controller。

CASE B
共享 state 成立，但 write family 没有 task headroom。
→ 修写入机制，不继续优化 selector。

CASE C
write 有用，但 history 不影响 action value。
→ 可以做自适应，但不能强主张 trajectory/state-dependent control。

CASE D
history 明显改变有益 action，
但 deployment-visible feedback 识别不了。
→ 研究 feedback / observability。

CASE E
history-dependent opportunity 存在，
而 measurement feedback 可以预测并利用。
→ 才进入完整联合 2×3、长期轨迹和外部验证。

任何一个 CASE 都是有效科研结果。

不要为得到 CASE E 修改实验定义。
